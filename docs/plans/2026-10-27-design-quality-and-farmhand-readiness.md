# Caddie design quality and Farmhand readiness — implementation plan

**Date:** 27 October 2026, Africa/Lagos. **Status:** model calibration completed; implementation proposed and not completed by this document. **Goal:** make the existing Caddie journey clear and trustworthy for someone who has never coded, and test the real Farmhand workflow before representing it as ready for judges. **Stack:** React, TypeScript, Cloudflare Workers/D1, Flue, isolated app previews. Existing implementation is in a dirty shared checkout: preserve all other work; integrate shared routes, contracts, migrations and ledgers serially. No deploy, paid model calls, GitHub changes, data reset or publication without the relevant authorization; this document grants none.

This is an evidence-led punch list from the conversation, the current code, previous local browser observations and the current public model catalog, not a claim that every combination of every surface has been audited. Verify the current screen and server before editing. Approved prior choices remain binding: compact cards with preserved decisions in Earlier; date-first personal Brief with Caddie; compact opportunity highlight with proportional alignment; focused project workspace; minimal Plan with optional technical detail; four destinations Plan / Build / Submit / Preview; mobile paired actions fill available width when they can fit. Respect the existing light/dark themes and responsive layouts. Do not redesign approved flows wholesale merely to create novelty.

## Decision rules for product design

- Start with the person's outcome, the current state, and the next useful action. Explain actual uncertainty and blockers in plain language. Do not require the person to interpret logs, models, repositories, hashes, test counts or provider configuration.
- Keep real evidence and developer controls reachable through clearly named optional details. A simplified screen must not conceal a relevant limitation, unapproved side effect, failed check or exact prior decision.
- Establish one type scale, 4/8-based spacing rhythm, surface hierarchy, icon style, border and input/button treatments. Reuse existing tokens and components rather than adding parallel ad-hoc styles; check all supported themes. Target 44px minimum touch areas and 16px mobile input text, 48px primary controls where appropriate. Respect safe areas and reduced-motion preferences.
- Prefer fewer distinct surfaces, short sentences, one primary action and intentional secondary actions. Avoid nesting cards within cards, duplicate headings/badges or many consecutive accordions. Information must wrap at narrow widths; no viewport-wide horizontal overflow. Do not force equal-height text blocks to truncate important status or rules.
- Motion should explain transition or progress, never imply work is progressing without evidence. Measure real interaction and network latency before optimizing; retain previous content on refetch and use bounded, cancellable loading. Test the real long conversation in addition to fixtures.

### Post-build change request — P0

**Known failing boundary:** `apps/app/src/server/build-workflow.ts` `requireBuildApproval` requires `workflow.phase === 'building'`. A ready project's natural-language request was sent to the coordinator without a valid new change admission, and its build calls were rejected. `setWorkflowBlocker` then moved the workflow to blocked. This is a product/harness lifecycle gap; the precise missing transition and interaction with current plan/design approval, spend payer, feature progression and file/version source must be reproduced in tests before choosing the implementation. Do not simply change `ready` to `building` or remove the approval check. The existing plan-hash approval cannot silently authorize a changed plan.

Design a durable **change request → scoped proposal → appropriate approval → bounded build → checks → new preview** lifecycle. Use an immutable base version and output; retain the last successful preview and allow it to be opened while a new change is pending, failed or cancelled. Material changes go through a review bound to the exact diff/scope and expected side effects; minor text changes may use an explicitly designed, policy-checked user-authorized path only if it can be proven safe. Publishing/merging/destructive changes remain separate decisions. Fence stale approvals, concurrent changes, retry/idempotency, attribution/spend and worker restarts. A failure must not silently poison the ready version or make the user debug tools. Reconcile the real Farmhand state with a supported recovery path, not manual DB surgery.

Starting points: `apps/app/src/client/project/AskForChange.tsx`, `apps/app/src/client/surface.tsx`, `apps/app/src/server/build-workflow.ts`, `apps/app/src/server/coordinator-host.ts`, `apps/app/src/server/routes/build-workflow.ts`, `apps/app/src/server/code-versions.ts`, `tests/build-workflow.test.ts`, `tests/browser/focused-project-chat.spec.ts`, `docs/plans/2026-10-26-build-reliability-continuation-handover.md`. Read `docs/flue-contracts.md` before agent work. Regression: start with a real ready project, request the text change, refresh/restart at each boundary, verify safe review/approval and new snapshot, ensure old preview persists; simulate failure, retry, duplicate and unauthorized operation. Verify the new visible wording and behavior—not merely a tool receipt. If that cannot be proven today, leave the old preview accessible and mark change editing BLOCKED; do not claim success.
